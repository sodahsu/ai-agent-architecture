# Skill: design-brief

## Purpose

把模糊的設計需求整理成可執行 Design Brief，明確定義問題、目標使用者、Scope、成功條件、限制與待決事項。

## Inputs

- Project / Feature Name（可選）
- Problem Statement
- Target Users / Context
- Constraints
- Existing Design Context（可選）

## Outputs

- Problem Definition
- Design Goals
- User Context
- In Scope / Out of Scope
- Success Criteria
- Constraints
- Open Questions

## Preconditions

- 至少知道要解決的問題或想改善的使用者狀態。
- 缺少資訊時先使用已知 Context；只有真正影響方向的缺口才提問。

## Permissions

- Read: task-relevant design context
- Write: brief artifact only
- External design tool write: none by default

## Procedure

1. 用一段話說清楚現在的問題與影響，不先跳到 UI 解法。
2. 定義 1–3 個 Design Goals，使用 Outcome 而不是活動描述。
3. 描述主要使用者、情境與核心痛點；未知部分標為 Assumption。
4. 明確列出 In Scope 與 Out of Scope。
5. 定義可觀察或可驗證的 Success Criteria。
6. 列出技術、商業、時程、Design System 等 Constraints。
7. 將尚未決定且會影響設計的事項列為 Open Questions。
8. 檢查 Brief 是否偷偷帶入私人、公司或客戶識別資訊；公開範例需要泛化。

## Validation

Brief 必須讓沒有參與前置對話的設計師也能理解：為誰解決什麼問題、這次做什麼與不做什麼、怎樣算成功。

## Failure Conditions

- Problem 與 Solution 混在一起到無法判斷真正需求
- Scope 完全沒有邊界
- Success Criteria 只能用主觀「好看／更有質感」描述且無法進一步具體化

## Completion Criteria

Brief 不含空模板欄位，Scope 與 Success Criteria 足以支持後續 Design Review / Design Spec 工作。
